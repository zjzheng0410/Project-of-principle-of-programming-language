# 项目总体架构设计

## 任务理解

本项目的核心目标不是直接手写一份固定功能的 C 程序，而是实现一个“示例语言文件 + 处理程序 -> 可编译 C 代码”的小型语言处理系统。示例文件必须能直接作为处理程序输入，处理程序读取其中的语言片段并生成 C 源文件，最终生成的 C 程序需要覆盖 `2026.docx` 中列出的 Option、函数式编程、数组处理、作用域、闭包、递归、条件表达式和 match 守卫等功能。

项目主体建议使用 C 语言完成：处理程序用 C 编写，生成目标也是 C 代码，运行时支持库也用 C 编写。除构建脚本和测试辅助文件外，不引入 Python 作为核心实现路径。

## 功能范围

- Option 能力：支持 `Some`、`None`、`is_some`、`is_none`、`match`、默认值、组合操作和链式错误传播。
- 函数式能力：支持函数赋值、匿名函数、函数返回函数、闭包捕获、闭包内部状态和高阶函数调用。
- 数组能力：支持数组字面量、索引、长度查询、遍历、映射、过滤、归约、任意/全部判定。
- 控制流能力：支持块级作用域、变量遮蔽、赋值、返回、递归、条件表达式和 match 守卫。
- 评测适配：处理程序不能只识别固定示例文本，应按功能语义处理同一范围内的修改版示例。

## 总体处理流程

示例源文件先进入源码读取与诊断模块，然后依次经过词法分析、语法分析、语义检查、闭包捕获分析、中间表示降低和 C 代码生成。生成结果由单个业务 C 文件和运行时库共同编译，运行时库只负责通用语言特性，不包含针对某个示例的硬编码逻辑。

分层依赖应保持单向：命令行层调用编译管线，前端只产出抽象语法树，语义层只做名字、作用域和类型检查，降低层把高级语言特性转换为更容易生成 C 的中间表示，代码生成层只负责输出文本，运行时库完全独立于处理程序内部结构。

## 根目录文件职责

- `README.md`：说明项目目标、输入输出关系、支持的语言特性和基本构建方式。它只写使用说明和功能边界，不承载实现细节。
- `Makefile`：统一构建处理程序、运行时库和生成后的示例程序。它只负责组织编译流程，不写业务逻辑。

## `examples/` 示例文件职责

- `2026_feature_demo.ppl`：作为综合示例文件，覆盖 `2026.docx` 中的主要功能，并用注释标明期望输出。它是评分时可直接输入处理程序的代表样例。
- `option_match.ppl`：聚焦 Option、match、match 守卫、默认值和链式传播。它用于验证 Option 相关能力不是通过综合样例硬编码实现的。
- `functional_array.ppl`：聚焦匿名函数、闭包、高阶函数和数组处理。它用于验证函数式能力与数组能力可以组合使用。

## `processor/` 处理程序文件职责

- `main.c`：处理程序入口，负责串联命令行解析、编译管线和退出状态。它不直接包含词法、语法或代码生成逻辑。
- `cli.h`：声明命令行参数结构和解析接口，隔离外部调用方式。它让主流程不依赖具体参数格式。
- `cli.c`：实现输入文件、输出文件、诊断级别等参数解析。它只处理命令行语义，不读取或编译源文件。
- `source.h`：声明源码缓冲区和源码位置查询接口。它为词法分析和错误报告提供统一的源码视图。
- `source.c`：负责读取示例文件并维护行列信息。它不理解语言语法，只提供稳定的文本访问能力。
- `diagnostic.h`：声明错误、警告和源码位置报告接口。它统一前端、语义层和代码生成层的错误表达。
- `diagnostic.c`：实现诊断信息格式化和输出。它保证错误信息短、清晰、可定位。
- `token.h`：定义词法单元类别、字面量范围和源码位置。它是 lexer 与 parser 之间的唯一共享词法契约。
- `lexer.h`：声明词法分析器接口。它隐藏扫描状态，向 parser 提供可预测的 token 流。
- `lexer.c`：实现标识符、数字、关键字、符号、注释和换行处理。它只负责把源文本转换为 token，不做语法判断。
- `ast.h`：声明抽象语法树节点类别和访问接口。它表达源语言结构，不绑定 C 输出形式。
- `ast.c`：负责 AST 节点创建、销毁和基础遍历。它集中管理语法树生命周期，避免 parser 和语义层重复处理内存。
- `parser.h`：声明语法分析总入口和解析结果接口。它作为表达式、语句和 match 子解析器的统一门面。
- `parser_expr.c`：解析字面量、变量、调用、数组、匿名函数、条件表达式和运算表达式。它只负责表达式层级和结合关系。
- `parser_stmt.c`：解析 let、赋值、return、块、函数定义和遍历语句。它维护语句边界，不处理 match 分支细节。
- `parser_match.c`：解析 match 结构、分支模式和守卫条件。它让 Option 匹配语法独立演进，避免主 parser 过长。
- `symbol.h`：声明符号表条目、名字绑定和查询接口。它是作用域检查与代码生成命名之间的桥梁。
- `symbol.c`：实现变量、函数、参数和内置名称的登记与查询。它不做类型推断，只保证名字解析一致。
- `scope.h`：声明词法作用域栈和变量遮蔽规则接口。它让块级作用域与闭包分析共享同一套作用域模型。
- `scope.c`：实现作用域进入、退出、遮蔽和外层查找。它确保局部变量与闭包捕获的边界清晰。
- `type.h`：声明语言层类型描述，如整数、布尔、数组、函数和 Option。它只定义类型概念，不负责检查过程。
- `type.c`：实现类型比较、组合类型构造和类型显示。它为诊断信息提供可读的类型名称。
- `semantic.h`：声明语义检查入口。它把 AST、符号表、作用域和类型检查组织成一个阶段。
- `semantic.c`：检查变量使用、函数调用、返回值、数组操作、Option 操作、递归引用和 match 分支一致性。它发现错误后直接报告，不做静默降级。
- `capture.h`：声明闭包捕获分析结果接口。它描述哪些外层变量需要进入闭包环境。
- `capture.c`：分析匿名函数和返回函数中对外层变量的引用。它同时标记可变捕获，支撑闭包独立状态。
- `builtin.h`：声明内置函数和内置语法能力注册接口。它让 `map`、`filter`、`reduce`、`len`、`is_some` 等能力有统一入口。
- `builtin.c`：维护内置名称、参数要求和返回类型规则。它避免这些规则散落在 parser、semantic 和 codegen 中。
- `ir.h`：声明中间表示的节点类别和访问接口。它把高级语言结构降为更接近 C 输出的结构。
- `ir.c`：负责中间表示对象的创建、销毁和遍历。它不直接读取 AST，也不直接写 C 文件。
- `lower.h`：声明 AST 到 IR 的降低入口。它是语义分析和代码生成之间的边界。
- `lower.c`：把闭包、match、Option 组合、数组高阶函数等结构转换为可生成 C 的中间形式。它不关心最终文本格式。
- `codegen.h`：声明 C 代码生成总入口。它向主流程隐藏表达式发射、语句发射和运行时引用细节。
- `codegen.c`：组织 C 文件整体结构、头文件引用、函数顺序和生成上下文。它不直接塞入大段表达式或语句生成逻辑。
- `emit_expr.c`：负责表达式级 C 输出，包括字面量、变量、调用、数组访问、Option 值和匿名函数调用。它只处理表达式片段。
- `emit_stmt.c`：负责语句级 C 输出，包括变量声明、赋值、返回、块、条件和循环式遍历。它只处理语句和函数体结构。
- `emit_runtime.c`：负责生成对运行时库的引用和必要初始化/清理片段。它保证生成代码和 `runtime/` 的依赖集中管理。
- `name_mangle.h`：声明内部命名转换接口。它防止源语言名称与 C 关键字、运行时符号或重复闭包名称冲突。
- `name_mangle.c`：实现稳定、可读、可回溯的 C 符号命名策略。它不参与语义判断，只服务生成阶段。
- `file_writer.h`：声明输出文件写入接口。它把代码生成文本缓冲和文件系统写入分离。
- `file_writer.c`：实现目录检查、目标文件写入和写入错误报告。它不修改输入示例文件。
- `arena.h`：声明处理程序内部临时内存分配接口。它用于统一管理编译过程中的短生命周期对象。
- `arena.c`：实现分阶段释放的内存池。它降低 AST、IR 和符号表对象的释放复杂度。

## `runtime/` 运行时文件职责

- `ppl_runtime.h`：运行时总入口头文件，汇总外部生成代码需要包含的接口。生成的 C 文件只应依赖这个总入口和必要的标准库。
- `rt_value.h`：声明运行时统一值表示。它为整数、布尔、数组、Option 和函数值提供共同边界。
- `rt_value.c`：实现值的创建、复制、比较和销毁。它避免数组、Option 与闭包模块各自重复管理值生命周期。
- `rt_option.h`：声明 `Some`、`None`、判定、默认值、组合和链式传播相关接口。它只暴露 Option 语义，不暴露内部存储细节。
- `rt_option.c`：实现 Option 的运行时行为。它保证 `None` 在组合和链式调用中按语义短路。
- `rt_array.h`：声明数组创建、索引、长度、遍历和高阶处理接口。它统一数组能力，避免生成代码直接操作底层内存。
- `rt_array.c`：实现数组存储、边界检查、映射、过滤、归约、any 和 all。它负责数组元素生命周期和错误定位。
- `rt_function.h`：声明函数值、闭包环境和调用适配接口。它是匿名函数、函数返回函数和闭包状态的运行时基础。
- `rt_function.c`：实现闭包对象、环境持有、调用分发和释放。它确保不同闭包实例拥有独立状态。
- `rt_builtin.h`：声明语言内置函数的运行时入口。它把 `len`、Option 辅助和数组辅助等能力集中暴露给生成代码。
- `rt_builtin.c`：实现内置函数到具体运行时模块的转发和参数检查。它保持生成代码简单，并让错误信息一致。
- `rt_memory.h`：声明运行时内存管理策略。它为值、数组和闭包提供统一的申请与释放入口。
- `rt_memory.c`：实现内存申请、释放和失败处理。它遇到无法恢复的内存错误时应直接报告并终止。
- `rt_error.h`：声明运行时错误报告接口。它统一数组越界、类型不匹配、空值误用和调用错误的表达。
- `rt_error.c`：实现运行时错误输出和退出策略。它让生成程序的失败位置清晰可查。

## `generated/` 输出目录职责

- `README.md`：说明该目录用于存放处理程序生成的 C 文件和临时构建产物。该目录内容应可删除再生成，不承载手写核心逻辑。

## `tests/` 测试资料职责

- `fixtures/option_match.ppl`：保存 Option 与 match 功能的测试输入。它用于检查示例修改后仍能被处理程序正确编译。
- `fixtures/closures.ppl`：保存闭包捕获、闭包状态、函数返回函数和递归相关测试输入。它用于检查函数式能力的边界。
- `fixtures/arrays.ppl`：保存数组字面量、高阶数组函数和聚合逻辑测试输入。它用于检查数组与函数值组合时的行为。
- `golden/option_match.out`：保存 Option 与 match 测试的期望输出。它用于和生成程序运行结果做文本级比对。
- `golden/closures.out`：保存闭包与递归测试的期望输出。它用于验证捕获状态和递归调用没有互相污染。
- `golden/arrays.out`：保存数组测试的期望输出。它用于验证 map、filter、reduce、any 和 all 的结果稳定。
- `test_plan.md`：说明手工与自动测试范围。它记录每类语言特性对应哪些输入文件和期望结果。

## 解耦与封装原则

- `.h` 文件只暴露必要接口，`.c` 文件隐藏实现细节；跨模块只通过头文件通信，不直接共享内部结构。
- parser 不做类型检查，semantic 不生成 C，runtime 不依赖 processor，generated 不反向依赖 processor。
- Option、数组、函数值、闭包和错误处理分别放在独立运行时模块中，避免一个巨大的通用运行时文件。
- 任何单个 `.c` 或 `.h` 文件接近 800 行时，应优先按职责拆分，而不是继续追加逻辑。
- 示例文件只描述功能和期望输出，不应成为处理程序内部的特殊分支条件。

## 推荐实现顺序

1. 先完成最小词法、语法和诊断框架，让处理程序能读取示例文件并报告可定位错误。
2. 再完成整数、布尔、变量、块级作用域、条件表达式和普通函数调用，形成可生成 C 的最小闭环。
3. 随后加入 Option、match、数组和内置函数，并把对应能力落到独立 runtime 模块。
4. 最后加入闭包捕获、函数返回函数、高阶数组操作和递归，补齐 `2026.docx` 的完整功能范围。
